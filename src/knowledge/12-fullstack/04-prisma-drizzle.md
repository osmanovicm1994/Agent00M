# Prisma and Drizzle (PostgreSQL)

Use the ORM the project already has. Check its installed major first: Prisma 7 and newer moved connection settings into `prisma.config.ts` and use driver adapters, so older `schema.prisma` examples may be wrong. Confirm with `npx prisma --version` and the docs tool.

## Both
- Schema is the source of truth; change it through migrations only (see `06-database/02-migration-safety.md`). Never edit an applied migration; never run a reset or `db push --force` against anything but a disposable local or branch database.
- One database client per process (a provider/singleton in Nest, a module-level instance in Next.js with a guard against hot-reload duplicates). Close it on shutdown.
- Map ORM types to DTOs at the boundary. Use transactions for multi-step writes. Select only needed columns on hot paths; load relations deliberately to avoid N+1.
- Add indexes for foreign keys and filter/sort columns; use unique constraints and handle their errors (`P2002` in Prisma; the Postgres `23505` code in Drizzle).
- Seeds are idempotent and never contain real data or secrets.

## Prisma workflow
- `npx prisma init --datasource-provider postgresql`; edit the schema; `npx prisma migrate dev --name <change>` locally (creates and applies the migration, regenerates the client); `npx prisma migrate deploy` in CI and production; `npx prisma generate` after dependency installs.
- With a pooled connection (Neon, PgBouncer) migrations need the DIRECT connection (see `05-neon-postgres.md`).
- "Client not generated" or type errors after a schema change: run `generate`.
- Comments in `schema.prisma` start with `//`. A `#` comment is a P1012 error on every such line.
- Prisma does NOT need Docker. It needs a reachable PostgreSQL database in `DATABASE_URL`. `prisma validate`, `prisma format` and `prisma generate` need no database at all (but Prisma 7's `env("DATABASE_URL")` in `prisma.config.ts` THROWS when the variable is unset: use the fallback in `13-delivery/03-recipe-nextjs-prisma-auth.md`), so run those first and do not wait on a database for them. `migrate dev`, `migrate deploy` and `db push` do need one. Use what the project already has: a hosted database (Neon, Supabase) in `.env`, a local Postgres, or Docker only when the project already has a compose file for it or the user asks. Never install or start Docker on your own to get a database.
- If `DATABASE_URL` is empty, a placeholder or unreachable, do not loop on migrate commands. Write the schema, run `validate` and `generate`, and report "migration not applied: no database reachable; need DATABASE_URL".

## Prisma version decides everything (check FIRST, before editing any import)
- Read the installed major: `npm --prefix <app> ls prisma @prisma/client` and look for `prisma.config.ts` / `prisma7.config.ts` and for `output = ...` in the generator block. If `@prisma/client` is missing from the app's package.json, `npx prisma` downloads the LATEST major (7) on the fly, which does not match an older schema: install `prisma` and `@prisma/client` into the app first.
- Prisma 6 and older (generator `prisma-client-js`): `import { PrismaClient } from '@prisma/client'`, `new PrismaClient()`, works in a NestJS CommonJS app. `npx prisma generate` writes into node_modules. If `@prisma/client` "has no exported member PrismaClient", the client was never generated or generate ran against a different install: run generate from the app folder that owns the schema.
- Prisma 7 (generator `prisma-client` with a required `output`, e.g. `../src/generated/prisma`): `@prisma/client` no longer exports a generated PrismaClient. Import it from the generated folder (`../generated/prisma/client`), never from `@prisma/client`. The connection URL moves out of `schema.prisma` into `prisma.config.ts`: `import "dotenv/config"; import { defineConfig } from "prisma/config"; export default defineConfig({ schema: "prisma/schema.prisma", datasource: { url: process.env.DATABASE_URL ?? "postgresql://user:password@localhost:5432/app" } });` (the import path is exactly `prisma/config`; a `url` line left in the schema is error P1012 "datasource property `url` is no longer supported"). Install with an explicit major: `prisma@7` and `@prisma/client@7`, because the npm `latest` tag can be a release candidate of the next major. `new PrismaClient()` needs a driver adapter: install `@prisma/adapter-pg` and `pg`, then `new PrismaClient({ adapter: new PrismaPg({ connectionString: process.env.DATABASE_URL }) })`. The generated client is ES-module code by default. If the app is ESM (`"type": "module"`, see `02-nestjs.md`) import it with the `.js` extension (`../generated/prisma/client.js`); a CommonJS NestJS app needs the generator option `moduleFormat = "cjs"` (confirm the option name with the docs tool). Passing `{}` to the constructor fails with "not assignable to PrismaClientOptions": that error means the adapter is missing.
- If the project has no reason to be on 7 and the rest of the stack assumes CommonJS (NestJS scaffold), pinning `prisma@6` and `@prisma/client@6` is the lowest-risk fix. Say so in the summary; do not silently downgrade a project that already uses 7.

## When the build keeps failing on the same area
- Read the whole error list once and group the errors by cause. If 8 of 9 errors are "Cannot find module './x'" for files that DO exist, fixing the one Prisma import will not help. The most common cause: package.json has `"type": "module"` and tsconfig uses `nodenext`, so relative imports need `.js` (see `02-nestjs.md`); fix ALL relative imports you wrote. Otherwise check `npx tsc --noEmit -p <app>/tsconfig.json --traceResolution` for the failing file, tsconfig `include`/`exclude`, and stale build info.
- Do not flip the same line back and forth (`.js` extension or not, `PrismaClient` import path) more than twice. If two attempts changed nothing in the error list, stop editing and report exactly what is unknown, for example: "build still fails with 9 errors; cause of the missing-module errors not found; need: tsconfig.json and package.json of apps/api, output of --traceResolution".

## Drizzle workflow
- Schema in TypeScript (`pgTable`), `drizzle.config.ts` with the dialect and credentials from env; `drizzle-kit generate` creates SQL migrations, `drizzle-kit migrate` applies them (review the SQL; avoid `push` outside local prototyping).
- Pick the driver to match the runtime: `node-postgres`/`postgres` for a long-running server, the Neon serverless/HTTP driver for edge or serverless.
